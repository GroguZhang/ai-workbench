## 1. 一句话定位与硬约束（先读这条，否则建议会跑偏）

**这是一套单人使用、跑在家里一台群晖 NAS 上、只对局域网开放的私人系统。它由两个独立子系统组成：**

| 子系统 | 角色 | 代码量 | 本文档章节 |
|---|---|---|---|
| **Card Vault** | 收藏档案库：录入、估值、图片处理、检索（主） | 3400 行 / 5 个文件 | §3–§10 |
| **cardhobby-radar** | 捡漏雷达：扫描二级市场挂单，判断"这条是不是漏"（旁挂） | 3746 行 / 1 个文件 | **§12** |

两者**不共享数据库、不共享进程**，只通过两个方向相反的只读挂载交换数据（§12.8）。
**§12 是一个完整独立的子系统设计，请把它和前面的 Card Vault 分开评价**——两者的约束不同：
雷达要面对的是不可控的外部网站、每天变化的行情感知、以及"判断错了会让人花真钱"的后果。

### 1.1 使用者与维护者的真实情况

| 项 | 实况 |
|---|---|
| 使用者 | 1 人（收藏者本人），偶尔在手机上录入 |
| 维护者 | 1 人，非职业后端工程师，主要靠 AI 辅助开发 |
| 可接受的运维成本 | **接近零**。不能要求"定期升级依赖""配置反向代理""维护 K8s" |
| 可接受的中断 | 不能接受数据丢失；可以接受偶尔服务重启 |
| 当前数据量 | 30 张卡 / 59 张图 / SQLite 约 100 KB / 图片约 16 MB |
| 3 年后的预估量 | 不超过 2000 张卡、4000 张图、约 1 GB |
| 雷达的运行强度 | 每天 2 轮定时 + 不定次手动刷新，每轮约 68 次外部请求、耗时 4 分钟 |

### 1.2 部署硬约束（这些是物理事实，不是偏好）

```
群晖 NAS DS220+（x86_64，Celeron J4025 双核，17.4 GB 内存，DSM 7.4.1）
  ├── 容器 card-vault（FastAPI，端口 8088:8000，restart: unless-stopped）
  │     ├── ./data/cards.db          ← SQLite，bind mount
  │     ├── ./uploads/               ← 实拍图，bind mount
  │     ├── ./app                    ← 挂载源码，模板改动刷新即生效
  │     └── ../cardhobby_radar/data  ← 只读挂载（只读消费雷达的数据）
  └── 容器 cardhobby-radar（纯标准库 Python 守护进程，无对外端口）
        ├── ./config                 ← 监控词库（JSON）
        ├── ./data                   ← hits.jsonl / calibration.json 等状态
        └── ../card-vault/data/radar_ctl ← 只读挂载（只读消费 Card Vault 的"手动刷新请求"）
```

由此产生的约束：

- **不能加"支撑性"的第二个容器**（Redis / Postgres / Celery / MQ）。雷达本身是唯一被允许的第二个容器，
  因为它是**完全独立的应用**（自己的代码、数据、生命周期），不是 Card Vault 的依赖。
  判断标准：新容器挂掉后 Card Vault 是否还能完整工作？能，才可以加。
- **不能用需要常驻内存的大框架**。这个 CPU 处理一张手机照片约 1.1 秒（OpenCV 透视矫正），已经很吃力。
- **SQLite 是刻意选择的**，不是妥协。单写入者 + 读多写少 + 数据量小 = SQLite 完全够用，而且备份就是复制一个文件。
  （雷达用得比 Card Vault 更极端：连 SQLite 都没有，全部状态是 JSON / JSONL 文件。）
- **前端不能上构建链**。没有 webpack / vite / npm。Jinja2 模板里直接写内联 JS + CSS，Bootstrap 走 CDN。
- **Card Vault 不能有后台定时任务**。所有耗时操作必须是用户点击触发的同步 HTTP 请求。
  唯一的定时逻辑在雷达容器里（自己的 `while True` 循环 + 20 秒轮询），不依赖 cron 或 systemd。

### 1.3 因此，什么叫"好建议"

| 好建议 | 坏建议 |
|---|---|
| 在现有单容器 / SQLite 内的改进 | 换数据库、拆微服务 |
| 让单人维护负担变轻 | 增加需要持续运维的组件 |
| 修真实会咬人的问题 | 提高"架构纯洁度" |
| 承认约束、说明代价 | 假设有团队和 CI/CD |
| 给雷达加"离线可复核"的能力（回测、参照价半自动） | 给雷达加"在线更强"的能力（LLM 实时判定、自动出价） |
| 降低误报，哪怕牺牲命中率 | 提高命中率，让人自己过滤 |

## 2. 运行时与部署实况（实测版本，别猜）

### 2.1 容器内实测依赖（从 `pip freeze` 抄的，不是 requirements 里写的）

| 包 | 版本 | 说明 |
|---|---|---|
| Python | 3.11.17 | 基础镜像 `python:3.11-slim` |
| fastapi | 0.143.0 | |
| starlette | **1.8.0** | ⚠️ 1.x 移除了 `TemplateResponse(name, {"request": ...})` 的位置参数写法，必须用关键字 |
| uvicorn | 0.54.0 | **未开 `--reload`**（改 `main.py` 需重启容器） |
| python-multipart | 0.0.32 | 文件上传 |
| Jinja2 | 3.1.6 | `keep_trailing_newline=False`（会吃掉一个尾部换行） |
| numpy | 2.4.6 | |
| pillow | 12.3.0 | EXIF 转正、缩放、JPEG 编码 |
| opencv-python-headless | 5.0.0.93 | 卡片检测与透视矫正 |

**系统包依赖**：`opencv-python-headless` 虽然不带 GUI，但仍动态链接 `libglib2.0-0` 和 `libgomp1`。`python:3.11-slim` 里没有，不装的话 `import cv2` 直接 `ImportError`。

### 2.2 依赖锁定策略

`requirements.txt` 里 FastAPI 全家桶**锁死精确版本**（历史事故：曾用 `>=`，重建镜像时拉到不兼容的 Starlette 1.x，首屏直接 500）。Pillow / numpy / opencv 只挡大版本（`>=10,<14` 等），因为它们的小版本几乎不会破坏 API。

### 2.3 部署方式（自己写的 SSH 脚本，没有 CI）

NAS 的 SFTP 子系统是关闭的，所以文件传输走 paramiko 的 exec 通道 + base64 + `sha256sum` 回验。部署分四级：

| 命令 | 做什么 | 何时用 |
|---|---|---|
| `nas.py upload` | 上传 + SHA256 校验 | 每次改完代码 |
| `nas.py sync` | 上传 + 重建容器（不重建镜像） | 日常改动，约 5 秒 |
| `nas.py deploy` | `docker compose up -d --build` | 改了依赖 |
| `nas.py verify` | 拉回容器内文件算 SHA256，四方比对 | 怀疑没生效时 |

⚠️ **`docker compose restart` 不会应用 `docker-compose.yml` 的卷变更**，改挂载必须 `up -d`（会重建容器）。

### 3.3 子系统之间怎么接（一句话版）

`cardhobby-radar/` 是一个**完全独立**的容器（`python:3.11-slim`，纯标准库 urllib，**无浏览器、无第三方依赖**），
每天定时抓取二级市场挂单、按球员规则筛出"疑似捡漏"，把命中流水 append 到 `data/hits.jsonl`。

Card Vault 只做两件事：
1. 用 `:ro` 挂载读它的 `hits.jsonl` 和 `radar_status.json`，渲染成 `/radar` 看板；
2. 在**自己的** `cards.db` 里建一张完全独立的 `radar_marks` 表，记录"已处理/已忽略"，并把"手动刷新请求"
   写进 `data/radar_ctl/`，反过来被雷达只读消费。

**铁律：雷达功能绝不写 `cards` 表。** 这条不是洁癖——`cards` 里是真实收藏数据，任何自动化写入都是在制造不可逆的脏数据。

**详细设计、定价公式、识别红线、学习闭环、校准方法、以及雷达自己的技术债，全部在 §12。**

## 4. 数据模型

### 4.1 `cards` 表（主表，唯一有业务意义的表）

```sql
CREATE TABLE IF NOT EXISTS cards (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    card_id           TEXT UNIQUE,      -- 业务主键，形如 "足球_20261013174902"（运动_本地时间戳）
    sport             TEXT,             -- 运动分类，中文，见 §6.2
    player            TEXT,             -- 球员名（中文名 + 英文名括号）
    year_set          TEXT,             -- 年份与系列，如 "2019 Topps Chrome"
    card_type         TEXT,             -- 卡种/平行版本，如 "Gold Refractor RC"
    serial            TEXT,             -- 编数，如 "0149/2026"，自然语言原样存
    est_raw_price     REAL DEFAULT 0,   -- 估值（人民币）
    cost_price        REAL DEFAULT 0,   -- 买入成本（人民币）
    status            TEXT DEFAULT '在库', -- 在库 / 送评中 / 代拍中 / 已售出
    grading_verdict   TEXT,             -- 评级预判意见（自由文本）
    notes             TEXT,             -- 备注
    img_front         TEXT,             -- 正面展示图文件名
    img_back          TEXT,             -- 背面展示图文件名
    img_front_orig    TEXT,             -- 正面原始图备份文件名（可能为空，用户已清理）
    img_back_orig     TEXT,
    photo_mode        TEXT,             -- 图片处理档位：auto / straighten / original
    rotate_front      INTEGER DEFAULT 0,-- 人工旋转角度（0/90/180/270）
    rotate_back       INTEGER DEFAULT 0,
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,  -- UTC
    updated_at        TEXT                                  -- UTC
)
```

设计要点：

- **`card_id` 与 `id` 双主键**：`id` 是数据库自增，`card_id` 是业务标识（含运动分类和创建时间，人可读、可用于图片文件命名）。所有对外 API 都用 `card_id`，`id` 只在排序/调试时出现。
- **`serial` 存原文**：不做结构化拆分。编数有太多写法（`0149/2026`、`/99`、`1/1`、`RC /2026`），强拆只会引入错误。
- **金额用 REAL**：不是 DECIMAL。这是私人收藏台账，不需要会计精度，浮点误差在 ¥0.01 级别无意义。
- **时间戳统一 UTC，`card_id` 里的时间戳是本地时间**：两者不同源，这是历史包袱。`card_id` 只当身份标识用，不影响业务，但**排序不能用它**（用 `id`）。
- **迁移是字典驱动的**：`MIGRATIONS = {"列名": "列类型"}`，`init_db()` 遍历它，缺列就 `ALTER TABLE ADD COLUMN`。只增不删，永不修改已有列。没有 Alembic。

### 4.2 `radar_marks` 表（旁挂，独立）

```sql
CREATE TABLE IF NOT EXISTS radar_marks (
    item_id  TEXT PRIMARY KEY,   -- 雷达那边的挂单 ID
    state    TEXT,               -- 已处理 / 已忽略 / 空（撤销）
    note     TEXT,
    updated_at TEXT
)
```

**和 `cards` 表零关系，零外键。** 这是刻意解耦：雷达的 ID 空间完全不受收藏库约束，雷达将来被删掉，这张表删掉即可，不影响收藏数据。

### 4.3 图片文件命名契约（重要的隐式契约）

```
uploads/
├── {card_id}_front.jpg            ← 展示图（处理后）。扩展名统一 .jpg
├── {card_id}_front.png            ← 仅"保留原图"档位才可能是原扩展名
├── {card_id}_front_orig{ext}      ← 原图备份（可能不存在：用户已清理以省空间）
├── {card_id}_back.jpg
└── {card_id}_back_orig{ext}
```

删除卡片时，不是"按 DB 里记的文件名删"，而是**按 `{card_id}_front` / `{card_id}_back` 前缀扫目录**。原因：`_orig` 文件名和展示图不同、历史版本可能残留别的扩展名，只按 DB 字段删会漏掉孤儿文件。

有一个需要小心的细节：`card_id` 可能在冲突时被追加 `_2` 后缀（`足球_2026...` → `足球_2026..._2`）。`A_2_front.jpg` 不以 `A_front` 开头，所以前缀扫描**不会**误删另一张卡的图——但这个巧合依赖命名规则，是脆弱的，见 §9.6。

## 5. 后端：关键实现

### 5.1 上传与图片写入的完整链路

```
浏览器 <input type=file> 选择手机照片
  → multipart 上传（可能 5–8 MB）
  → save_upload(upload, card_id, side, mode, rotate, keep_orig=True)
      → 读全部字节到内存（有 MAX_INPUT_PIXELS=5000 万像素的进件限制）
      → run_process(raw, mode, rotate)      ← 失败则**退回原图**，绝不吞掉上传
      → store_photo()                        ← 写三个文件：展示图 / 原图备份
  → 更新 DB 的 img_* / img_*_orig / photo_mode / rotate_*
```

**关键设计：`run_process` 失败时退回原图。** 用户上传了照片，处理算法挂掉了，正确的行为是"这张图按原样存下来"，而不是"整个录入失败"。宁可要一张没裁切的图，也不要用户白填一遍表单。

### 5.2 排序白名单（用户输入永不进 SQL 文本）

```python
SORTS = {
    "price_desc": "估值 高→低", "price_asc": "估值 低→高",
    "pnl_desc": "盈亏 高→低",  "pnl_asc": "盈亏 低→高",
    "cost_desc": "成本 高→低", "newest": "最新录入", "oldest": "最早录入",
}
_SORT_SQL = {
    "price_desc": "COALESCE(est_raw_price, 0) DESC, id DESC",
    "price_asc":  "COALESCE(est_raw_price, 0) ASC, id DESC",
    # 没填成本的卡得到 NULL，DESC 时沉底，而不是当成成本 0 拿全额估值冒充暴利霸榜
    "pnl_desc":   "(CASE WHEN cost_price > 0 THEN COALESCE(est_raw_price,0)-cost_price END) DESC, id DESC",
    "pnl_asc":    "(CASE WHEN cost_price > 0 THEN COALESCE(est_raw_price,0)-cost_price END) ASC, id DESC",
    "cost_desc":  "COALESCE(cost_price, 0) DESC, id DESC",
    "newest":     "id DESC",
    "oldest":     "id ASC",
}
DEFAULT_SORT = "price_desc"

def sort_sql(name):
    """返回 (排序键, ORDER BY 片段)。未知值一律回落到默认排序，不报错。"""
    key = name if name in _SORT_SQL else DEFAULT_SORT
    return key, _SORT_SQL[key]
```

三个刻意的选择：
1. **白名单查表**，不是拼接过滤。用户输入只能"命中"或"回落"，无法构造 SQL。
2. **每档都挂 `, id DESC` 兜底**。否则同价卡片的先后会随 SQLite 内部行序抖动，看起来像 bug。
3. **未知值静默回落默认，不报 400**。前端传了个旧版本的键、或者有人手动改 URL，都不该看到错误页。

响应体里额外回一个 `"sort": 实际生效的键`，方便排查"为什么排出来是这个顺序"。

### 5.3 前端如何消费

```javascript
fetch('/api/cards?sport=' + encodeURIComponent(sport) +
                 '&status=' + encodeURIComponent(status) +
                 '&sort=' + encodeURIComponent(sortValue()))
```

⚠️ **必须 `encodeURIComponent`**。中文参数（`?sport=足球`）原样塞进 URL，uvicorn 底下的 h11 会直接回 `400 Invalid HTTP request received`，因为 HTTP 请求行只允许 ASCII。

### 5.4 维护类批量接口

| 接口 | 用途 | 保护 |
|---|---|---|
| `POST /api/maintenance/reprocess-all` | 重算全部图片 | 必须带 `confirm=yes`，跑完写 `data/last_reprocess.json` 留痕 |
| `POST /api/maintenance/drop-originals` | 清除原图备份释放空间 | 同上 |
| `POST /api/cards/{card_id}/reprocess` | 单张重算（可带 mode / rotate） | 无 |

这三个接口**没有鉴权**（因为整个应用就没有鉴权，见 §9.1）。

### 6.2 运动分类：一个被低估的难点

收藏者录卡时，运动分类是**自由输入**（`<input list="sport-options">` + `datalist`），不是下拉选择。因为运动种类太多，限制死会逼人撒谎。

所以有一套归一化逻辑：

- `SPORT_LABELS`：22 项常用分类（含"其他"），用户没想好时可选。
- `SPORT_MAP`：英文/别称 → 中文（`soccer`→足球、`baseball`→棒球、`basketball`→篮球…）。
- **子串匹配按键长降序**（`SPORT_KEYS_BY_LEN`）：否则 `football` 会先吃掉 `american football`，把橄榄球错认成足球。
- **认不出的运动原样保留**，不丢空、不归"其他"。用户写"匹克球"就存"匹克球"。
- 筛选器由 `SPORTS_IN_VAULT` **数据驱动**：只列出库里真实存在的分类，不列全部 22 项。

### 6.3 弹层栈（Esc 键的正确行为）

页面有 4 个 Bootstrap Modal + 1 个自建灯箱。照片灯箱是从详情 Modal 里打开的，所以**同时有两层**。

`Esc` 的行为必须是"关最上面那层"，而不是"全关"或"关详情但留下灯箱"。实现是自己维护一个 `isOpen(id)` 栈查询 + `closeTopLayer()`，而不是依赖 Bootstrap 的 `keyboard` 选项（多个 Modal 同时开着时它行为不可靠）。

## 7. 图像流水线（`photos.py`，项目里最复杂的一块）

### 7.1 要解决的问题

收藏者用手机拍卡，得到的是这样的照片：桌面背景、卡片歪着、透视变形、4 MB、方向靠 EXIF。目标是**整齐美观**：每张卡都裁紧、拉正、压缩到合适大小。

### 7.2 流水线步骤（**顺序不可变**）

```
原始字节
  → ① EXIF 方向烘焙（ImageOps.exif_transpose，把旋转写进像素）
  → ② 超大图预缩小（> 5000 万像素才触发，防 NAS 内存吃紧）
  → ③ 卡片检测（三种策略并行出候选：Otsu 亮区 / Canny 边缘 / Otsu 反相）
  → ④ 评分选优 + 透视矫正（getPerspectiveTransform + warpPerspective）
  → ⑤ 二级收紧（_tighten，去掉残余背景，带单调性约束）
  → ⑥ 缩放到长边 1400 + JPEG q=85
  → ⑦ 人工旋转（rotate 参数，0/90/180/270）
  → 输出（无 EXIF）
```

### 7.3 检测算法的实际形态

```
候选生成  → approxPolyDP 拟合四边形（poly4）
          → 失败则退回 minAreaRect
          → 校验：凸性、面积占比（6%–94%）、宽高比（0.45–1.00）、直角余弦（>0.45）
          → 打分：frac * (0.45 + 0.55 * aspect_prior(宽高比))，aspect_prior 以 2.5/3.5 为峰
          → 两轮：粗检 + _tighten 收紧
```

### 7.4 实测效果（63 张真实手机照片）

| 指标 | 数值 |
|---|---|
| 检出并裁切成功 | 63 / 63 |
| 宽高比落在 0.714 ± 0.12 内 | 95% |
| 体积 | 235.3 MB → 16.4 MB（7.0%） |
| 耗时 | DS220+ 上约 1.1 秒/张（端到端，含 HTTP），63 张共 66 秒 |
| 自动旋转的图 | **0 张**（见 §8 决策 #1） |

### 7.5 三个档位

| 档位 | 行为 | 何时用 |
|---|---|---|
| `auto`（默认） | 检测裁切 + 转正 + 压缩 | 常规 |
| `straighten` | 只 EXIF 转正 + 压缩，保留完整画面 | 检测失败、或者想保留拍摄背景 |
| `original` | 完全不处理 | 特殊卡 |

原图备份默认保留（`_orig`），用户确认效果后可以批量清理（已经清理过一次，235 MB → 0，用"移入回收目录 + SHA256 先验证"的方式做的，不是 `rm`）。

## 8. 十个关键设计决策 + 理由

### 决策 #1 ⚠️ 绝不做任何基于几何的自动旋转

**曾经的做法**：`FORCE_PORTRAIT = True`，"检测框是横的，就说明卡拍倒了，转 90°"。
**动机**：看到一批输出是横向的，主观认为"卡片都该是竖的，所以横向 = 有 bug"。
**结果**：交付了错图。8 张被它处理的照片里，横版卡、横着放进卡砖的卡，**透视矫正结果本来就是正的**，转 90° 反而全转歪了。用户反馈原话是"为什么有几张卡是反的 这种错误不能出现啊"。

**根本原因**：一张"竖版卡躺倒拍摄"和一张"横版卡正常拍摄"在几何上**完全同构**，只靠轮廓无法区分。任何基于几何的自动旋转都是猜，而猜错 = 交付错图。

**现在的规则**：方向只由 EXIF（`exif_transpose` 已处理）+ 用户手动 ↺ ↻ 决定。代码里留了一个 `FORCE_PORTRAIT = False` 的常量，注释里写了完整的翻车记录，防止后人再打开。测试里有哨兵断言：`assert photos.FORCE_PORTRAIT is False`。

### 决策 #2 二级收紧必须带单调性约束

`_tighten`（检测后紧贴着卡片再收一圈）在"卡片装在卡砖里 / 近正方形画面"上会把比例改**差**：实测把 4 张从 0.78 拉到 0.96（离标准卡比例 0.714 更远）。

修法：收紧结果如果**翻转了横竖**，或者**离标准卡比例更远**，就一律不采纳。

```python
if (bw > bh) != landscape_before:
    return bgr, False
after = min(bw, bh) / float(max(bw, bh))
if abs(after - CARD_ASPECT) >= abs(before - CARD_ASPECT):
    return bgr, False
```

效果：比例达标率 79% → 95%。

### 决策 #3 删除图片按前缀扫目录，而不是按 DB 字段删

只按 `img_front` 删会漏掉 `_orig` 备份和历史上其他扩展名的残留。改成按 `{card_id}_front` / `{card_id}_back` 前缀扫 `uploads/` 目录。

三重保护：只接受 basename（挡路径穿越）、必须以前缀开头、删前删后报文件数与字节数。

### 决策 #4 数据安全优先于一切自动化

`cards` 表里是**真实收藏数据，不是测试数据**。因此：

- 任何删除/修改必须用精确 `card_id`，禁止模式匹配批量操作。
- 改 DB 前先 `cp data/cards.db data/cards.db.bak-<时间戳>`。
- 清理孤儿图必须**先列清单、用户确认后再删**，且删除动作是"移到一个带时间戳的回收目录"，不是 `rm`。
- 测试一律用临时 `DATA_DIR`，不碰真实库。

### 决策 #5 时间戳一律 UTC 存储，前端换算

历史数据混用过本地时间和 `CURRENT_TIMESTAMP`（UTC），统一改成 `datetime.now(timezone.utc)`。前端 `fmtLocal()` 换算成本地展示。

例外：`card_id` 里的时间戳是本地时间（人类可读性优先），只当身份标识，不参与任何计算。

### 决策 #6 深色主题下必须显式覆盖 Bootstrap 的表格/卡片变量

Bootstrap 的 `.card` / `.table` / `.modal` 会设 `color: var(--bs-body-color)` = `#212529`（深色）。这些样式是**为浅色背景设计的**，铺在 `#0f172a` 的深色底上，就是"深字压深底"，对比度 **1.05:1**，肉眼完全看不见。

曾经因此让用户以为"很多字体颜色完全看不清"，排查了好几轮。

修法：

```css
.card-dark {
  color: var(--vault-text);          /* 必须显式写，不能靠继承 */
}
.table {
  --bs-table-color: var(--vault-text);
  --bs-table-bg: transparent;
  --bs-table-border-color: var(--vault-line);
  --bs-table-hover-color: var(--vault-text);
  color: var(--vault-text);
}
```

同类陷阱：`.btn-outline-danger`(#dc3545)=3.23:1、`.btn-outline-secondary`(#6c757d)=3.12:1、`.text-secondary`=3.12:1、`.text-success`=3.23:1 —— 全都是按浅底设计的。

**验证方式不能靠肉眼**：`_deploy/shoot.js` 用 CDP 驱动真实 Chrome，遍历每个文本节点、逐级向上求第一个不透明背景色、算 WCAG 对比度。

### 决策 #7 手机端整表转卡片流

`/radar` 表格有 6 列。在 390px 视口下横向溢出 166px，把唯一的行动按钮"去抢"挤出屏幕。

修法：`@media (max-width: 576px)` 下隐藏 `thead`，`tr` 变卡片，`td[data-label]` 用 `::before` 显示字段名。

### 决策 #8 排序/筛选铁律：能不能行动，比新旧更重要

雷达看板的排序不是按时间，而是**"能抢的"永远在"不能抢的"前面**，已截标的一律沉底。因为用户打开这个页面的唯一目的是"现在还能抢什么"。

同理，`expired` 严格用 `deadline_ts <= now`，**不加任何宽限**。一旦加缓冲，就会出现"倒计时写着已结束、卡却还在待抢页"的自相矛盾——比少看一张更伤信任。

### 决策 #9 前端下拉的选项与后端白名单必须交叉校验

前端 `#filter-sort` 的 7 个 `<option>` 是**静态写死**的（不用 `/api/sorts` 动态填充，避免首屏闪一下）。这就产生了"两侧可能漂移"的风险：改了后端忘了改前端，用户选了一个后端不认的键，静默回落默认，用户会觉得"排序坏了"。

修法：`test_parse.js` 里用正则解析 `main.py` 的 `SORTS` / `_SORT_SQL` / `DEFAULT_SORT`，与 HTML 里的 `<option value>` 逐字比对。同时断言 `main.py` 里必须出现 `/ORDER BY " \+ order_by/`（即只能拼白名单片段，不能拼变量）。

### 决策 #10 `localStorage` 读回来的值必须先校验合法性

`vault.sort` 存着用户上次选的排序。但版本迭代可能下线某一档，此时旧值不在 `<option>` 里，`select.value = 'old_key'` 会静默失败，select 显示成空白，用户不知道为什么。

修法：读回来先 `Array.some(options, o => o.value === saved)`，不合法就用默认值。

## 9. 已知技术债与风险清单（**我已经知道了，请直接给方案，不要重复指出**）

### 9.1 【最高优先级】整个应用没有任何鉴权

任何能访问 `http://<NAS内网IP>:8088` 的人，都能读取全部收藏、上传图片、删除卡片、甚至调用 `/api/maintenance/reprocess-all` 重算全部图片。

**当前的风险判断**：只在局域网、只有家人能访问、NAS 本身有防火墙 → 暂时可接受。

**但如果**将来想做成"在外面也能看"，或者家里有访客 WiFi 和设备隔离不严，这就是个洞。

**我卡在哪**：不想引入用户体系（一个人用，注册/登录/密码找回全是负担）。可能的轻量方案：
- 单个共享口令 + 签名 Cookie（无 DB 表）
- HTTP Basic Auth（nginx 层或 FastAPI 中间件）
- 局域网 IP 白名单
- 群晖本身的反向代理 + 访问控制

**想听你说**：在"一个人用 + 不能加容器 + 不能接受复杂配置"的约束下，哪个方案的**长期维护成本最低**？以及"不做"的风险到底有多大（考虑到它只在局域网）。

### 9.2 `main.py` 已经 1392 行，`index.html` 1578 行

单文件极简的代价。目前还能"从上往下读 300 行定位"，但雷达部分（1072–1330 行，约 260 行）和卡片部分**完全没有业务关联**，只是共用一个 `app` 对象。

**自然的拆法**：雷达相关的路由 + 模板拆成 `app/radar.py`（`APIRouter`），`main.py` 只剩卡片。但拆了之后 `nas.py` 的部署清单要跟着改，而且会引入"两个文件都要记住"的心理成本。

**想听你说**：这个拆分值不值得做？如果不值得，1400 行继续长下去的临界点在哪、到那时该用什么方式止损？

### 9.3 没有鉴权 + 没有事务的写操作

`add_card` / `update_card` 里是"先处理图片写文件，再 INSERT/UPDATE DB"。如果写文件成功但 DB 失败，会留下**孤儿图片**（无 DB 引用）。反向的情况（DB 成功但文件丢失）也可能。

目前靠 `_deploy/orphan_scan.py` 定期只读扫描 + 人工确认清理来兜底，没有自动修复。

**想听你说**：在 SQLite + 文件系统的组合下，用什么模式能让"文件与 DB 的一致性"不依赖人工巡检？（写 temp 再 rename？先写 DB 后写文件？定期对账任务？）

### 9.4 Bootstrap 走公网 CDN（`cdn.jsdelivr.net`）

国内移动网络下 `jsdelivr` 不稳定。一旦加载失败，整个页面掉光 Bootstrap 样式——看起来像"代码 bug"，实际是网络问题。

**已知修法**：把 Bootstrap CSS/JS 下载到本地，用 `app.mount("/static", ...)` 提供。约 200 KB，改完就永不依赖外网。

**为什么还没做**：需要改 Dockerfile / 加 `static/` 目录 / 改两处 `<link>`，属于"知道该做但一直没排上"。

### 9.5 数据库备份是手动的

目前靠"改 DB 前手动 `cp cards.db cards.db.bak-<时间戳>`"，且备份文件会**无限累积**在 `data/` 目录里。

**想听你说**：在没有 cron、只有 Docker 的前提下，最简可靠的自动备份方案是什么？（容器启动时备份一次？每次写操作后保留 N 份轮转？还是依赖 NAS 的 Hyper Backup 快照？）

### 9.6 图片命名的前缀扫描依赖命名规则

`safe_remove_uploads` 靠"文件名以 `{card_id}_front` 开头"判断归属。如果 `card_id` 里出现下划线，或者将来引入别的后缀约定，前缀匹配可能误判。

目前 `card_id` 格式是 `{运动}_{时间戳}`，运动名里目前没有下划线，所以安全。但这是个**隐式契约，没有断言保护**。

### 9.7 没有分页 / 没有虚拟滚动

`fetchCards()` 一次拉全部卡片，全量渲染。当前 30 张没问题，2000 张时：
- 单次响应约 2000 × 1 KB = 2 MB JSON
- DOM 里 2000 个卡片节点 + 4000 个 `<img>`（虽然有 lazy loading）

**想听你说**：在"不能加构建链、不想引入前端框架"的前提下，最轻的分页或虚拟滚动方案是什么？服务端游标分页 + 前端"加载更多"按钮？

### 9.8 雷达的 `hits.jsonl` 会无限增长，每次请求全量重读

`/api/radar/hits` 每次都读整个 JSONL 文件（append-only 流水），内存里过滤出"最大 `scan_id` 那一代"。文件会一直长。

### 9.9 前端图片没有尺寸变体

每张展示图都是长边 1400、约 250 KB。列表页卡片缩略图只需要 400px 宽，却加载了 1400px 的原图。30 张时无所谓，2000 张时首屏流量会很惨。

### 9.10 没有导出功能

数据全在 SQLite 里。用户想"把全部收藏导成 Excel 看看"必须手动从 NAS 拷 db 文件。没有 CSV/Excel 导出接口。

## 10. 明确的设计红线（提建议时不要违反）

1. **不要加"支撑性"的第二个容器。** 不要建议 Redis / Postgres / Celery / Nginx 容器 / 独立 worker。
   （雷达是例外，见 §1.2 的判断标准；但**不要**为了给雷达加能力而再引入第三个容器。）
2. **不要上构建链。** 不要引入 npm / vite / webpack / React / Vue / Svelte / TypeScript 编译。
3. **不要引入 ORM。** SQLite + 手写 SQL 是刻意选择，`sqlite3` 标准库足够，ORM 会让"一个人半年后读懂"变难。
4. **不要建议自动旋转图片。** 见决策 #1，这条已经被真实交付事故证伪。
5. **不要动 `cards` 表的既有列定义。** 只能 `ADD COLUMN`，不能改类型/改语义（历史数据会错）。
6. **不要让雷达模块写 `cards` 表。** 见 §3.3。
7. **不要"为了提高测试覆盖率"而加测试。** 现有 350+ 断言测的都是真实会咬人的地方（方向、删除、对比度、排序白名单漂移）。加覆盖率数字没有价值。
8. **不要建议重写。** 单人维护的项目，"重写"的隐性成本永远被低估。
9. **不要建议给雷达上 LLM 做识别。** 见 §12.10 的理由。要么给出一个能在**每天 2 轮 × 68 关键词 × 60 条/页**的量级下、成本可控且判定可复现的方案，否则不要提。
10. **不要建议降低判定的严格度来"提高命中率"。** 这个雷达的错误代价是不对称的：漏掉一条是少赚一次，误报一条是让人花真钱买错东西。宁可漏，不可错。

## 12. 旁挂子系统：捡漏雷达（cardhobby-radar）

> 这一节是**一个完整独立的系统设计**，请和 §1–§11 的 Card Vault 分开评价。
> 它的技术栈比 Card Vault 更极端（无第三方依赖、无数据库、无框架），但面对的问题更脏（外部网站、人工判断、真金白银）。
> 如果时间有限，**优先看 §12.4（识别层）、§12.5（定价链）、§12.9（技术债）、§12.10（为什么不用 LLM）**。

### 12.1 它要解决什么问题

在"卡淘"（国内球星卡交易平台，形式接近定时截标的拍卖）上，每天有几千条新挂单。
我固定关注 68 名球员，其中真正值得抢的卡可能一天只有个位数。
手工翻是翻不过来的，而且**判断"这条便不便宜"必须在那条挂单还活着的时候完成**——截标之后一切分析都只是复盘。

所以这个系统的唯一职责是：**在截标之前，把"值得出价的挂单"和"我最多该出多少钱"送到手机上。**

它刻意不做的事：

- 不自动出价、不登录、不操作账户。**只读公开列表页**。出价永远是人的动作。
- 不判断卡品真伪（只看标题自述的瑕疵词，且只降权不拦截）。
- 不碰 Card Vault 的数据库。

### 12.2 运行形态

| 项 | 实况 |
|---|---|
| 部署 | 独立容器 `cardhobby-radar`，官方 `python:3.11-slim`，**零第三方依赖**（只用 urllib / json / re） |
| 构建 | **不构建、不装包**，只把这个 `.py` 以 `:ro` 挂进镜像 |
| 触发方式 | 容器内 `while True` 循环 + 20 秒轮询（**不用 cron、不用 systemd**） |
| 定时轮次 | 每天 2 轮：**17:00 摸底**（截标窗口 ≤ 5.5h）/ **19:20 终局**（窗口 ≤ 3h） |
| 手动轮 | 网页点一下 → Card Vault 写一个请求文件 → 雷达 20 秒内取走执行（窗口 ≤ 3h，**不推送**，否则每刷一次手机就响一次） |
| 每轮负载 | 68 个关键词 × 最多 3 页 × 60 条，4 线程并发，约 4 分钟，请求间隔 0.8 秒 |
| 推送渠道 | PushPlus（微信）/ Bark（iOS）/ 企业微信 webhook，可同时配 |
| 状态存储 | **没有数据库**。全部是 JSON / JSONL，原子写靠"写临时文件 + `os.replace`" |

```
data/
├── hits.jsonl            命中流水（append-only，每条带 scan_id；超 5000 行裁到最近 3000）
├── radar_status.json     上一轮体检结果（原子替换）
├── radar_state.json       当前是否正在扫描（供网页显示"正在扫…"）
├── radar_snapshots.json  盘口快照（同一张卡 17:00 vs 19:20 的价与出价次数）
├── watch_track.json      待回填成交的登记表（截标后 10 分钟去抓真实成交价）
├── closed_fills.jsonl    真实成交价流水（**事实**，不是判断）
├── calibration.json      校准因子（档位级 + 全局级）
├── learned_rules.json    学习出的规则（排除词 / 非签字名单 / 人工降档）
├── vault/feedback.jsonl  ← Card Vault 写（只读挂进来）：我标记的"判断错了"
└── vault/approvals.json  ← Card Vault 写：我采纳了哪条学习建议
```

### 12.3 一轮扫描的完整数据流

```
卡淘 SearchCommodity API（返回 JSON，需 PC User-Agent）
   │  按截标时间升序，所以第 1 页就是最早结束的一批；整页都在窗口内才翻下一页
   ▼
解析 + 窗口过滤（remaining_minutes <= max_hours × 60）
   ▼
识别层（§12.4）
   ├─ 整包 / 原箱 / 套盒  → 拦截
   ├─ 多人卡（lot）        → 拦截
   ├─ 认错人 / 串名        → 拦截
   └─ 通过
   ▼
档位判定（双轨制）
   ├─ 签字轨 auto_tiers：/10 及以下 → /25 → /50 → /99 → /199 → /399 → 基础无编签 → Case Hit
   └─ 折射轨 parallel_tiers：无签字但带编的折射 / 平行版本
      （"不是签字卡"学习规则会把卡强制赶到折射轨 = 降档但不拦卡）
   ▼
定价（§12.5）→ 得到「红线买入价」
   ▼
决策
   ├─ bid_count = 0                    → 起拍观察（blind）：要求起拍价 ≤ 红线×0.5 且期望利润 ≥ ¥150
   ├─ 现价 + 运费 ≤ 红线                → 真漏（steal）
   ├─ 现价 + 运费 ≤ 红线 × 1.20         → 准漏（near_miss）
   └─ 其余                             → 丢弃
   ▼
封顶（每人 ≤ 2 条；真漏 24 / 准漏 10 / 起拍 12，按期望利润排序后截断）
   ▼
写 hits.jsonl（带 scan_id）+ 登记 watch_track.json
   ▼
推送（有漏推战报 / 无漏推心跳 / 接口全哑推告警）
```

**为什么必须有 `scan_id`**：`hits.jsonl` 是 append-only 流水，不是"当前名单"。
网页只认最大 `scan_id` 那一代。不这么做的话，规则收紧后被拦掉的卡会永远沿用旧记录挂在页面上——
真实事故：连续两轮给某个球员加上排除词之后，页面上那几条"321 倍回报"的假信号怎么刷新都不消失。

### 12.4 识别层（最容易出错、也最贵的一层）

**总原则（用户明确要求）：判定以球员英文名为准，中文名只负责检索召回。**
理由：卡淘标题是卖家手写的，中文译名极度混乱（同一个人 3–5 种写法），而英文名相对稳定。

**① 中文短简称会嵌进别人名字内部 —— 这是最阴的一类错误**

| 标题片段 | 假命中的球员 | 真相 |
|---|---|---|
| 凯沙**德约**翰逊 | 德约科维奇 | 是 Kyshawn，音译里恰好含"德约" |
| 若昂贝兰热**贝林**格 | 贝林厄姆 | 另一个人的音译 |
| 玛丽亚**萨卡**里 | 萨卡 | 女网球员 Sakkari |
| **马克西**莫 | 马克西 | 名字就是"马克西莫" |

守卫 `player_name_matched()` 的规则：候选子串**后面紧接一个音译字**、且它**不是某个更长词条的前缀** → 不认。
再叠加每条球员自己的 `exclude_words`。

**② 英文名绝不能拆单名**

`Luka` 同时命中 Luka Doncic 和 Luka Garza。规则：英文只认**全名**、**姓氏**、或**长度 ≥6 的名**
（`Giannis` 这种卖家只写名字的要认）。但姓氏必须保持整体：`Gilgeous-Alexander` 不能拆成 `Alexander`，
否则一个网球选手会冒充 SGA。

**③ 串名规则（规则 B）**

标题里**自己的英文名没出现、别的监控球星的英文名出现了** → 判定串名，拒绝。
场景是卖家写"模板 XX""队友 XX""接班 XX"，这类词有单独的 `RIVAL_WORDS` 处理。

**④ 纯中文标题默认不认**

中文 keyword ≤3 字 + 标题含拉丁字母 ⇒ 必须找到本球员英文名（`en_name_verified`）才算通过。
实测 1686 条中文命中里 37.5% 找不到英文名，其中 2/3 已被上面的规则拦掉，
剩下的几乎全是 `阿罗科达雷`（含"科达"）、`马尔科达格拉卡`、多人 lot —— 纯中文单卡可忽略不计。

几条"看起来像但不是"的拦截：

- **`可累计` 不能进拦截表**——多半是"运费可累计"，单卡也这么写。
- **`带原盒` 要先剥离**再判断，否则原盒卡会被当成"卖盒子"拦掉。
- 封箱 / 整包 / 套盒 有独立的强、弱两张模式表（`SEALED_PATTERNS` / `SEALED_WEAK_PATTERNS`）。
- **`三级/3级` 里的 `/3` 不能被当成 /3 限量编**——编号正则必须做负向量词排除。
  这条错过一次：一张 ¥1 的 Base 卡被判成"埋价 ¥432 的 /3 极低编"。

### 12.5 定价链（六个乘数连乘 + 两级校准）

这是整套系统里**最需要外部审视**的部分。

```python
# 起点：词库给每个 (球员, 档位) 两个人工数字
#   tier.max_buy_rmb    红线买入价（我愿意出的上限）
#   tier.ebay_ref_rmb   参照价（eBay 成交行情，已折人民币）

multiplier = 1.0
multiplier *= 1.15 if 卡签(on-card)                      # (a) 卡签溢价
multiplier *= 1.20 if 高端系列(Sapphire/Finest/国宝…)     # (b) 系列溢价
multiplier *= 1.15 if 首编/尾编/1-of-1                    # (c) 特殊编号溢价
multiplier *= 评级壳系数(按 PSA/BGS 分数段)                # (d) 约 1.0 ~ 1.45+
multiplier *= 0.75 if 标题自述瑕疵(角损/白边)              # (e) 残卡折价
multiplier *= 0.55 if 兑换板(非实物)                       # (f) 兑换板折价

红线 = tier.max_buy_rmb  × multiplier × 校准因子
参照 = tier.ebay_ref_rmb × multiplier × 校准因子

# 两级校准（优先级从高到低）
#   本档位因子：同一球员同一档位 ≥3 笔真实成交，封顶 ±45%
#   全局因子：  ≥4 笔成交合并算，地板 0.45，上限锁死 1.0（只许下调）
#   都没有 → 1.0
# 人工判断"档位偏高"：×0.9^n，地板 0.60。与成交校准分开算。
#   成交是市场事实，人工是"我觉得贵"，所以给温和权重；但必须真能咬人。

回收价 realizable = 参照 × 0.70        # 变现率：扣平台佣金 / 国际运费 / 汇损
期望利润 profit_at_red = realizable − 红线
门槛：profit ≥ ¥40 且 ROI ≥ 1.6x，否则整条丢弃
```

**三个关键判断（都被真实事故验证过）：**

1. **绝不能把"起拍价"当"当前价"**。接口里 `Price` 几乎恒为 `1.00`（起拍价），`LowestPrice` 才是当前价。
   搞混的那一版产出 985 条"真漏"、全是 ¥1、还把推送打到 413。**这条错了，整个产品就是幻觉。**
2. **排序不能用"现价买入的倍数"**。¥1 起拍时那个数字是几百倍，看着爽但毫无意义。
   统一用 `profit_at_red`（按红线买入还能赚多少），它衡量的是"这个档位值不值得追"。
3. **¥1 起拍 + 0 出价 ≠ 能 ¥1 买到**。要单独看浏览量（`out_count`）、出价次数、剩余时间，
   折算成"竞争烈度"提示。0 出价的卡不算"漏"（成交价还没被市场验证），只进"起拍观察"区。

**两级校准的由来**：档位级样本永远攒不够（68 人 × 十几个档位，每月几十笔成交）。
而真实偏差其实是**平台级**的——参照价来自 eBay 美元 comps，成交发生在卡淘国内场。
首轮 20 笔真实成交算出来：**成交/参照 中位数 0.34，即参照系统性虚高约 2.9 倍**。
所以全局因子是有解释力的，不是拍脑袋。

### 12.6 学习闭环（三级，每一级都真的改行为）

反馈来源是网页上的"有误"按钮，六类原因，**每一类都有不同的后果**：

| 原因 | 后果 | 门槛 |
|---|---|---|
| 认错人 | 提炼该球员的排除词 | ≥2 次 |
| 不是单卡 | 整包 / 凑套词 | 直接生效 |
| 不是签字卡 | 提炼**系列 / insert 名**进全局非签字名单；采纳后只按折射轨估 | 1 次 |
| 编号认错 | 连**解析片段**一起记进 `serial_suspect` | 直接 |
| 档位偏高 | 按 (球员, 档位) 累计 **×0.9^n，地板 0.60**，真的乘到参照价上 | 直接 |
| 重复 / 已下架 | L1 永久拦截该 item_id | 直接 |

**为什么"不是签字卡"只降档不拦卡**：非签字卡不是没价值，只是低一档。拦掉会漏掉真实的便宜货。

**为什么"档位偏高"必须真的乘**：这一项起初只是记录项，用户抱怨"只能选它"——根因是**点了没用**。
假反馈比没有反馈更伤信任。

**踩过的坑**：非签字候选词必须剔除所有人名。
首跑把 `lamine`（Lamine Yamal 的名）和 `yamal` 当成系列名，采纳后会让该球员全部降档——**学反了比不学更糟**。
现在用全体 `en_name` 分词建黑名单，并叠加 `SET_WORDS_LOWER`。

**另一条硬规则**：无编号的纯特卡降档后折射轨接不住（折射轨要求必须有编或 Case Hit）→ **直接不报价**，宁可漏不可错。

**处置与判断分离**：`radar_marks`（在 Card Vault 里）= 我怎么处置这张卡；
`feedback.jsonl` = 雷达判断错了。前者不参与算法，后者才喂学习。

### 12.7 截标结算（唯一能拿到"真相"的地方）

定价链全靠"参照价"，而参照价是人工抄的。唯一能验证它的是**真实成交价**。

```
每轮扫描前先做三件事（顺序不能反）：
  1. harvest_closed_fills()   回填上一批已截标的真实成交价
  2. recalibrate_tiers()      重算校准因子（依赖成交）
  3. rebuild_learned_rules()  重算学习规则（依赖反馈）
  → 三者都必须在评估本轮候选之前就位
```

回填机制：

- 所有命中（**抢没抢都记**）登记进 `watch_track.json`，记录截标时刻。
- 截标 +10 分钟后抓 `/market/item/{id}`。该页服务端直出 `id="currentPrice"` 和 `id="bidcount"`，
  **截标后仍可读**，`bidcount=0` 即流拍。这是唯一稳定可靠的真相来源。
- 写进 `closed_fills.jsonl`。

**一个反直觉的坑**：`closed_fills.jsonl` 是**事实**，不受 `scan_id` 约束。
因为没抢到的卡会被新一批挤掉出最新一代 `hits.jsonl`，如果回填也只认最新一代，
那么"离场卡"的成交价永远拿不到，`filled` 恒为 0，校准永远攒不到样本。
所以回填要给掉出流水的卡**反向补行**。

### 12.8 两个子系统怎么交换数据（方向对等的只读）

```
cardhobby_radar/data/       → 挂到 card-vault 的 /app/data/radar:ro   （读流水、读体检）
card-vault/data/radar_ctl/  → 挂到 radar 的 /app/data/vault:ro        （读手动刷新请求）
```

**两边都是 `:ro`，谁也不能写对方的数据目录。** 只暴露 `radar_ctl` 一个子目录，`cards.db` 不在其中。
手动刷新的交互靠"Card Vault 往**自己的**目录写一个请求文件，雷达只读它，并把已处理的 id
记在**自己的** `rescan_seen.json` 里"。

这个做法很土，但有个好处：**任何一个容器挂掉，另一个都能完整工作**，且没有共享状态可以损坏。
代价是延迟（最长 20 秒）。

由此产生的几个细节：

- **截标时刻 = `scan_ts + remaining_minutes × 60`**。接口里的 `end_time_str` 只有 `HH:MM`，反推跨天必错。
- **`expired` 严格 `deadline_ts <= now`，不加宽限**。加缓冲会出现"倒计时写着已结束、卡却还在待抢页"
  的自相矛盾，比少看一张更伤信任。
- **同店合邮必须在网页端重算**（`same_seller_count` 按 consignor 在**未截标**命中里重数）。
  雷达的 `enrich_same_seller_shipping()` 在 `record_hit()` **之后**才跑，流水里没这个字段；
  而且已截标的卡不能再合邮，算进去就是虚报收益。
- **推送的坑**：PushPlus 业务失败仍返回 HTTP 200（`code:999`，内容超 2 万字）。
  必须解析 body 的 `code == 200` 才算成功，并按字符预算裁剪正文（`PUSH_MAX_CHARS`），不能拍固定条数。

### 12.9 雷达的已知技术债（同样：**我已经知道了，给方案就行**）

**R1｜3746 行单文件，零类型标注，零模块划分。**
改一条识别规则要在一个文件里跳四五个函数，`run_radar_scan` 一个函数就 200 行。
拆分（抓取 / 识别 / 定价 / 校准 / 推送 / 调度）是显而易见的方向，但拆完之后
"一个人从上往下读"这个优势会消失一部分。**这个取舍值不值得？什么时候做？**（对应 Q5 的同类问题）

**R2｜识别层是正则 + 人工词库，本质脆弱。**
每发现一个假命中就加一条排除词，词库只会越来越长，且新规则可能压住旧规则（见 §12.6 的 `lamine` 事故）。
这是"不断打补丁"的路，我知道它会越来越难维护，**但暂时看不到不用 LLM 前提下更好的路**。见 Q9。

**R3｜9331 行人工词库是最大的单点成本，而且会过期。**
68 名球员 × 十几个档位 × 2 个人工数字（红线价、参照价），全靠我从 eBay comps 手抄，行情一变就失真。
**这是我最想自动化、也最不敢自动化的地方**——自动化错了比人抄错了更危险（见 Q11）。

**R4｜两级校准：档位级攒不够，全局级是一把钝器。**
全局因子现在把所有球员所有档位按同一比例压缩（地板 0.45）。
参照本来准的卡（实测里像"某人 /25 橙折 58%"）会被无差别低估。
档位级需要 ≥3 样本，在 68 人规模下一个月都攒不到几个。**见 Q8。**

**R5｜完全没有回测能力。**
改一条规则只能等第二天实盘看效果，而且"今天没漏"和"规则太严"无法区分。
手上其实有 `hits.jsonl`（历史每一代判断）+ `closed_fills.jsonl`（真实成交），理论上可以离线回放，但没做。**见 Q10。**

**R6｜单点，没有外部健康检查。**
daemon 进程挂了，唯一信号是"今天没收到心跳"，而心跳本身也由同一个进程发。
NAS 重启靠 `restart: unless-stopped` + `--run-on-start` 补跑；
但如果是进程活着、调度循环卡死，没有任何告警。

**R7｜无重试、无退避。**
`_request_search_page()` 是单次 `urlopen(timeout=20)`，失败即返回空。
一次网络抖动 = 该球员这一轮直接跳过（计入 `errors`，但不重试）。
多轮下来，"某球员连续几天 0 命中"和"他真没货"看起来是一样的。

**R8｜没有数据库，状态散在 10 个文件里。**
原子性靠"写临时文件 + `os.replace`"，但**跨文件一致性没有任何保证**。
比如 `watch_track.json` 写成功、`hits.jsonl` 写失败，就会出现"追踪了一张页面上没有的卡"。
也因为没有索引，网页端每次都要全量读 `hits.jsonl`（有 5000 行上限兜底，见 §9.8）。

**R9｜反爬完全靠礼貌。**
0.8 秒间隔 + 4 线程 + 单 UA，没有 UA 池、没有代理、没有指纹伪装。
目前够用（量小），但如果对方改策略，没有任何缓冲层。

**R10｜"竞争烈度"是纯启发式。**
`out_count` + `bid_count` + 剩余时间 → 三档提示。权重是我拍的，
**没有任何数据验证过它和"最终成交价 / 是否抢到"的相关性**。
而它直接决定了"0 出价的卡要不要进观察区"这个动作。

### 12.10 为什么明确不用 LLM 做识别（提前回答，省得你建议）

考虑过，暂时否掉，理由是可验证的：

1. **量和成本**：每天 2 轮 × 68 关键词 × 最多 3 页 × 60 条 ≈ 每天上万条标题。
   逐条过 LLM 是每天上万次调用，成本和延迟都不成立。
2. **可复现性**：同一个标题今天判"是"明天判"否"，我就无法解释为什么昨天推了今天没推。
   而这个系统的全部价值建立在"我出价时相信它的判断"上。
3. **可回放性**：没有回测能力（R5）时，黑盒判定会让"改规则 → 看效果"这个循环彻底断掉。
4. **错误方向**：LLM 倾向于"看起来像就说是"，而这里需要的是"拿不准就说不"。

**但如果你是建议"用 LLM 做离线辅助"**（比如帮我从 eBay comps 里抽参照价、
或从历史成交里挖出新的假命中模式），**那是另一回事，我很欢迎**——
因为那是在离线、可复核、出错不影响实时判断的前提下用。
