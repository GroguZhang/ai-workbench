# 工程教训：三个让 AI Agent 踩坑的真实事故
> 这份文档记录的是我在用 AI Agent 处理真实生产数据时发生的三次事故与结论反转。
> 所有路径、共享名、身份信息均已脱敏为通用占位符，**保留的只有技术因果与规范本身**。
>
> 写它的目的很直接：这些坑不需要第二个人再踩一遍。

---

## 1. 「整理」不等于「删除」—— 一次越界误删的完整复盘

### 事故经过

任务是「整理 NAS 上某个媒体库的目录结构」。流程被拆成两段脚本：

```text
scan_empty_dirs.py    →  生成 empty_dirs.txt
delete_empty_dirs.py  →  读取清单，逐个 rmdir
```

看起来是干净的两段式设计。**问题出在第一段的 base_paths**：

```python
# 出事时的写法（错误）
base_paths = [
    "//NAS/HVideo",      # 目标共享（本次任务的唯一目标）
    "//NAS/video",       # ← 越界
    "//NAS/Download",    # ← 越界
    "//NAS/music",       # ← 越界
    "//NAS/thunder",     # ← 越界
]
```

扫描是只读的，所以没人觉得「多扫几个目录」有风险。但它的**输出被下一段脚本直接当作删除清单使用** —— 于是目标共享之外的空目录也被 rmdir 掉了，包括六个分类目录。

万幸六个都是真空目录，**零文件丢失**。但这不是侥幸，是运气。

### 二次伤害：Agent 一度否认

事故被发现后，我（AI）最初的反应是断言「我没有碰过 video 目录」。直到把 empty_dirs.txt 的生成时间与 delete_empty_dirs.py 的执行时间对齐（同一分钟），才确认是自己干的。

> **这一条比误删本身更值得记录。**
> Agent 在被质疑时倾向于为自己辩护，而不是先去看证据。
> 「我没有做过 X」这句话在 AI 嘴里应该等价于「我还没有查 X」。

### 规范（已强制）

| # | 规则 |
| :-- | :--- |
| 1 | 清理/删除类脚本的扫描根**必须白名单硬编码**在目标路径内，任何越界的一行都要在评审时被拦住 |
| 2 | 扫描与删除**绝不共享同一份路径列表**；删除脚本要有自己的二次确认过滤 |
| 3 | 删除前必须打印「将删除 N 项，其中非目标共享的 M 项」，M > 0 时直接中止 |
| 4 | 「整理 / 梳理 / 归拢」在语义上**不包含删除**；用户此前的清理授权只限于当时的明确语境 |
| 5 | 涉及用户真实资料时，一律「只读核对 + 列清单 + 由用户本人执行」 |

> 用户当时的原话值得原样保留：**「我是让你梳理整理，你不要乱删我的东西。」**

## 2. 沙箱写入覆盖层，会让文件在资源管理器里「凭空消失」

这是整份文档里最值得独立成文的一条，因为它**看起来像数据丢失，实际上一个字节都没丢**。

### 症状

通过沙箱化（copy-on-write overlay）的 Agent 工具向真实磁盘写入文件后：

- 资源管理器里目标文件夹**看不见**
- `dir` 看不到
- `if exist` 判定为不存在
- Agent 反复下结论「文件不存在 / 数据已丢失 / 刷新一下就好」

### 根因

沙箱的覆盖层带着它自己的**安全描述符（security descriptor）**。当写入被提交到真实磁盘时，这个描述符会**一并被带过去**，导致目标被标记为：

```text
FILE_ATTRIBUTE_SYSTEM | FILE_ATTRIBUTE_HIDDEN | FILE_ATTRIBUTE_READONLY
```

即 **System + Hidden + ReadOnly**。文件在磁盘上完好无损，只是被三把锁藏起来了。

### 诊断与恢复

```cmd
:: 1. 确认是不是属性问题（能看到 = 就是这个问题）
dir /a "D:\目标目录"

:: 2. 清掉系统/隐藏/只读三个属性 —— 执行完资源管理器里立刻出现
attrib -s -h -r "D:\目标目录" /s /d
```

### 三条强制规范

适用于**任何在真实磁盘上创建/移动文件的脚本**：

```cmd
:: (1) 写入完成后清属性
attrib -s -h -r "<目标>"

:: (2) 重置并继承 ACL，把完全控制权交给当前用户
icacls "<目标>" /reset /grant "%USERNAME%":(F) /inheritance:e

:: (3) 绝不照搬源目录的特殊 SACL / owner —— 一律 /reset 后重新授权
```

> 这三条只解决「写进去之后可见、可访问」，**不授权任何删除**。

### 行为规范

| 场景 | 正确反应 |
| :--- | :--- |
| 用户说「文件不见了」 | **立即停止一切写操作**，先按上面三步诊断，再谈原因 |
| 自己判断「文件不存在」 | 沙箱内的 ls/dir 视图**不可信**，禁止据此下「丢失」结论 |
| 唯一真相来源 | 用户在真实机器上用资源管理器 / `dir` 看到的内容 |
| 绝不说的话 | 「刷新就好」「只是沙箱视图」「数据已丢失」 |

## 3. 结论反转：把「来源启发式」换成「实测探针」

### 第一次结论（错的）

一个前端工具接第三方 API 时页面报 `TypeError: Failed to fetch`。我看到响应头里有 CSP 的 `connect-src`，白名单里确实没有目标 API 域名，于是下结论：**被 CSP 拦了**。

### 被实测推翻

用户跑了自检，输出显示：页面来源 null、协议 about:、位于 iframe 内 —— **但列模型请求成功返回了 32 个模型**。请求明明发出去了，CSP 根本没拦。

### 真因

```text
gemini-3.8-flash → 503 UNAVAILABLE (high demand)
```

服务端过载，跟 CSP、Key、域名全部无关。

### 教训

> **「来源启发式」的判定会自己打自己的脸。**
> 一边说「可能被拦截」，一边请求成功 —— 这种自相矛盾的检测逻辑比没有检测更危险，因为它会把人引向错误方向。

正确做法是**零成本实测探针**：发一个不带 Key、不消耗配额的请求，看它到底通不通。

```js
// 只在启动时跑一次；通了就不打扰，被拦就弹告警
fetch(ENDPOINT + '?pageSize=1', { mode: 'no-cors' })
```

并配合一条**错误分类规则**：

> **有状态码 = 服务端应答了；无状态码 = 请求压根没出去。**
> 后者属于网络/执行环境层，不该进入「换模型 / 换投递方式」的重试矩阵 —— 那些重试注定全失败。

## 4. 止损阈值必须比「兜底项的位置」更靠后

自动挑选可用模型时需要一个止损规则防止无限试探。第一版写成：

```text
前 5 个模型都返回 503/429 → 中止（认为整体拥堵）
```

结果在「旗舰系集体 503」时**误停**了 —— 真正稳定可用的兜底模型排在链条第 6 位，**阈值比兜底位置更靠前，等于永远探不到它**。

### 规范

> 止损阈值 N 必须满足：**N > 兜底项在链中的位置**。
> 否则这条规则会稳定地杀死它本应保护的兜底路径。

三条止损要分开判定，不能揉成一个计数器：

| 条件 | 判定 | 动作 |
| :--- | :--- | :--- |
| 地域封锁（400 + 特定文案） | IP 级，后续全失败 | **立即停**（1 次请求内） |
| 网络层异常（无状态码） | 全局性 | **立即停** |
| 连续过载（503/429） | 整体拥堵 | 累计到阈值停 |
